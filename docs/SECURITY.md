# Security model — EvanBo

Run locally with a dedicated SQLite database and trusted registered Git roots. The shipped server binds to loopback. Network-facing deployment, reverse proxies and multi-user OS separation have not been accepted.

Scoped bearer identities protect APIs by project, role, assignment and expiry. The operator CLI and direct SQLite filesystem access have the OS user's authority; possession of the database file is not a sandboxed agent credential. Protect the database, token files, backups and source roots using OS permissions. Browser cookies are read-only and separate from worker/manager writes.

SQL data uses parameters. Resource paths reject traversal, absolute paths, backslashes, NUL, colon, Git symlink and submodule traversal. Repositories are explicitly registered by a trusted operator. Git object existence is not semantic test verification. Source strings are untrusted project data and must not be followed as new instructions.

Transactions use immediate writes, foreign keys, a five-second busy timeout and WAL after migration. Exact duplicate bundle submissions are idempotent. Five seconds of contention can return an error; callers must retain the original key/body and check the receipt. No claim of unbounded concurrency, power-loss certification, network filesystem safety, or adversarial same-user filesystem isolation is made.

Fixes in this candidate: route-selector authorization, HEAD parity with GET, cross-project dependency rejection/read filtering, Git deletion impact events, node-scoped submission receipts (schema v8 with migration), dependency events only on real inserts, removal of the legacy `events` mirror (owner-visible compatibility decision), rejection of unknown submission fields, rejection of an empty global read bearer, resource-selector reads (node/architecture/context/history) return 404 for missing, foreign and project-mismatch resources, while project-scoped collections keep 403 for an out-of-scope project, 401 for missing/expired/revoked identities on scoped writes, and 404 (not 500) when a local-source snapshot is absent. Existing V1 data is not deleted to hide defects. New tests include a killed process with an active transaction and cross-process replay/restart checks.

This repository contains no communications bridge or scheduler implementation. Optional legacy schema import functions parse historical JSON/YAML as data; they do not contain a commercial harness or model implementation. The old Python/speaker adapter is outside this Rust-only release scope, and its missing-source test failure remains in the private audit.

The locked dependency set was checked with `cargo-audit` 0.23.0 against the RustSec advisory database at commit `4ef2df8e806a65e2f1ecc14f56f51249062b23d6` (2026-11-13). RUSTSEC-2026-0459 (bundled SQLite before 3.54.0 via `libsqlite3-sys`) was fixed by moving to `rusqlite` 0.41.1 / `libsqlite3-sys` 0.39.1 (SQLite 3.54.1); the audit now reports zero vulnerabilities. Informational warnings remain (`unsafe-libyaml` unmaintained; `rustix` and `tokio` unsound advisories) and are recorded in the review evidence. A local secret-pattern scan and code review are not a complete legal or dependency audit; re-check the exact Cargo.lock against a current advisory database before publishing. Report findings privately to the author; no public security contact has been designated in this review candidate.

## MCP adapter

Task assignment is manager-only (`POST /v1/map/nodes`); a worker can read/write its own assigned node and may request other nodes through the manager/operator (no self-service elevation). Worker scope is the bound node context: the worker may read that node, its direct children and dependencies, and project-level history/source metadata, but cannot select another node or project. Field-level filtering is not claimed; the scoped web viewer is local/non-scoped and has no browser Bearer flow, so do not expose it directly on a scoped deployment without a trusted reverse proxy.

`map-mcp` is a local stdio process. Legacy host-task validation is explicit opt-in via the `map_host_compat` marker table; an unrelated table named `tasks` alone cannot change identity decisions. It exposes only authenticated `map_resume`, `map_project` (reader/manager), and bound `map_submit`; it never calls the unbound operator mutations. It uses existing map transactions and role checks. Tokens come from MAP_AGENT_TOKEN or a private regular token file (0600 on Unix), not tool arguments. Tokens and source payloads are not logged. stdin lines are bounded at 128 KiB, tool arguments at 64 KiB, results at 1 MiB. It supports the negotiated legacy MCP revision 2025-06-18 only; it does not claim modern 2026 stateless protocol, HTTP MCP, prompts, sampling or resource subscriptions. EOF ends the process. A killed process may have committed a submission; retry the exact key and payload.

Schema v9 scopes each artifact key and its verification/digest to one project. An operator must register the canonical Git root and link its key to the project before a submission can use it. Two projects may register the same repository. A local Git check establishes that an object exists at that revision, not that tests passed. The operator CLI and direct database access trust the OS user; scoped HTTP/MCP roles do not isolate hostile processes running as that user. The HTTP viewer is optional.

Before upgrading a nonempty database, migration writes a SQLite backup alongside it. IDs, links and receipts are preserved. A legacy artifact with no single registered owner across its node and checkpoint associations is retained with NULL project_id and excluded from project reads, even if a project is subsequently registered. Same-project historical values are retained, not recertified. Inspect anomalies with docs/inspect-legacy.sql. Verify provenance against the original repository and resubmit under the correct project; preserve the old receipt. To roll back, stop writers and restore the before-map-v9 backup to a new path using the prior binary; later writes are not in that snapshot.

An artifact marked verified establishes Git object existence. Its digest is optional. For a new checked digest, the operator supplies the lowercase SHA-256 of the raw blob at the registered root and revision. The store streams and checks those bytes before committing. For a tree or commit, omit the blob digest. Worker declarations can neither fill nor change a verified digest. Promotion by an existence-only Git check discards a previously unverified digest. On a database written by older candidates, a historical verified digest has unknown provenance. Recheck such rows with artifact_checked against the original Git blob before relying on them.

Artifact checks and Git change scans ignore local replacement refs. The immutable revision must be a full Git object ID (40 or 64 hexadecimal characters). A historical digest from an earlier candidate, including one checked before replacement refs were disabled, requires revalidation against the original object.

Schema v10 archives every legacy verified claim in map_legacy_artifact_verifications. For an artifact with a registered owner the live row becomes unverified with no digest. Quarantined rows remain invisible. Bindings, checkpoints and exact retry receipts retain their IDs. A migration does not access Git. Use artifact_checked on the canonical registered repository to certify an owned row again. For operator inspection run docs/inspect-legacy.sql. The pre-upgrade SQLite backup preserves the source database. Stop writers before rollback and restore the backup at a new path using the previous binary.
